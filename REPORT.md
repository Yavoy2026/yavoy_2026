## 1. О чём проект

**YaVoy Travel Group** — кроссплатформенный агрегатор туристических экскурсий по России (аналог Tripster/Sputnik8). Три роли пользователей:

- **Туристы** — ищут, фильтруют, бронируют экскурсии, ведут избранное, смотрят Reels (видео-истории в стиле TikTok), получают бонусные баллы, общаются с AI-поддержкой.
- **Партнёры (B2B)** — организаторы туров: регистрация по ИНН/ОГРН с верификацией ФНС, публикация туров, кабинет с KPI, клиентами, транзакциями, отзывами и чатом.
- **Администраторы** — модерация анкет партнёров, туров, Reels, ответов на отзывы; управление пользователями и ролями; редактор юридических документов; email-рассылки; чаты.

Проект сгенерирован/ведётся через платформу **Rork** (AI-генерация приложений) — см. `rork.json` и `expo/README.md`.

## 2. Стек технологий

Одно и то же приложение реализовано **на четырёх платформах параллельно**:

| Платформа | Директория | Стек | Объём (файлов кода) |
|-----------|-----------|------|---------------------|
| Expo (iOS/Android/Web) | `expo/` | Expo SDK 52+, expo-router, React Query, AsyncStorage, lucide-react-native, expo-video | 56 |
| Web | `web/` | Vite, React, react-router-dom, shadcn/ui, Tailwind, React Query, react-hook-form + zod | 83 |
| iOS нативный | `ios/` | Swift 6, SwiftUI, MVVM (@Observable), iOS 18+ | 25 |
| Android нативный | `android/` | Kotlin, Jetpack Compose, Material 3, Ktor Client, Coil 3, Koin, minSdk 24 | 23 |

**Бэкенд** — внешний, в репозитории отсутствует: `https://yavay.ru/backend/api/v1`. По формату ошибок (`err.detail`) и схемам эндпоинтов это, по всей видимости, FastAPI (Python).

## 3. Домены предметной области

1. **Каталог экскурсий** — Tour (26+ полей), города, категории (транспорт, интерес, сезон, длительность), поиск, фильтры, сортировка. *Сейчас — мок-данные.*
2. **Бронирование и платежи** — бронирования, транзакции, ваучеры, коды подтверждения, скидки, предоплата, политика отмены. *Мок.*
3. **Пользователи и авторизация** — JWT (access + refresh), роли, профиль, фото. *Единственный домен, реально работающий через API.*
4. **Лояльность** — бонусные баллы, промо-коды «пригласи друга», подарочные сертификаты. *Мок.*
5. **UGC / контент** — Reels (видео + модерация), отзывы, ответы партнёров на отзывы. *Мок.*
6. **Партнёрский (B2B)** — анкеты ИНН/ОГРН, верификация ФНС, туры на модерации, гости, выручка, KPI. *Мок, включая «верификацию ФНС».*
7. **Администрирование** — модерация всего, роли, юр. документы, рассылки. *Частично API (роли/активация на Web), остальное мок.*
8. **Коммуникации** — чаты клиент↔партнёр↔админ, AI-поддержка (Rork Toolkit LLM), уведомления. *Мок / внешний LLM.*

## 4. Что уже сделано

**UI/UX-слой практически завершён** на всех четырёх платформах (с разной полнотой — подробная матрица в `PROJECT_DOCS.md`, §12):

- Полная навигация: 4 вкладки + детали тура, Reels, авторизация, поддержка, админ-панель, партнёрский кабинет.
- Дизайн-система: токены цветов, светлая/тёмная/системная тема с локальным сохранением.
- Каталог с поиском, 5 видами фильтров, сортировкой, геолокацией (Expo).
- Детали тура: галерея, бейджи, политика, точка сбора с картой, отзывы, модальное бронирование.
- Партнёрский кабинет: 5 вкладок, многошаговая регистрация.
- Админ-панель: до 10 вкладок (Expo).
- Авторизация через реальный API с авто-рефрешем токенов (Expo, Web, Android).
- Пара smoke-тестов на Web (`web/src/test/`), на остальных платформах тестов нет.

**Ключевой факт: это витрина на мок-данных.** Каталог туров (20 туров, ~2900 строк моков в Expo), бронирования, платежи, Reels, партнёрка, модерация, чаты — всё локальное. Реальный API покрывает только auth и users.

## 5. Есть ли API?

**Да, но минимальный.** Реализован и подключён (Expo: `expo/services/api.ts`, Web: `web/src/services/api.ts`, Android: `network/ApiService.kt`; iOS — полностью на моках):

- **Auth:** `POST /auth/signin`, `POST /auth/signup`, `GET /auth/whoami`, `GET /auth/logout`, `GET /auth/refresh`
- **Users:** `PATCH /users/{id}` (профиль), `.../change-password`, `.../photo`, `.../update-role`, `POST .../activate`, `DELETE .../deactivate`, `GET /users/photo/{filename}`, `GET /ping`

Клиент грамотный в основе: кэширование токенов, дедупликация параллельных refresh-запросов (`refreshPromise`), прозрачный повтор запроса при 401, единый `ApiError`.

**API не существует** для: туров, поиска, бронирований, платежей, избранного, отзывов, Reels, лояльности, партнёрки, модерации, чатов, уведомлений — то есть для ~90 % функциональности продукта.

## 6. Оценка плана по созданию API

Формального плана в репозитории **нет** — `PLAN.md` описывает продукт/дизайн, `PROJECT_DOCS.md` §7 фиксирует только текущее состояние. Оцениваю фактический (неявный) план «auth-first, остальное потом» и существующий дизайн API как фундамент.

### Что сделано правильно

- Начать с auth/users — верно: это сквозная зависимость всех остальных доменов.
- Версионирование в URL (`/api/v1`) заложено сразу.
- Пара access/refresh токенов с авто-обновлением — правильная модель для мобильных клиентов.
- Клиентский слой изолирован в одном модуле на платформу — подключать новые эндпоинты будет дёшево.

### Критические пробелы плана

1. **Нет контракта.** Отсутствует OpenAPI-спецификация. Четыре клиента пишут типы руками, и они уже разошлись: в API-клиентах роль `moderator`, в доменных типах — `manager` (`PROJECT_DOCS.md` §7.2 vs §8.4). Без единого контракта расхождения будут множиться в четырёх кодовых базах.
2. **Нет порядка выкатки доменов.** Логичный порядок по ценности: каталог туров (read-only) → бронирования + платежи → отзывы/избранное с синхронизацией → партнёрка → модерация → чаты/уведомления. Каталог — самое дешёвое и самое ценное: он read-only, разблокирует реальный продукт и убирает 3000 строк моков.
3. **Не спроектированы сложные домены.** Бронирование требует идемпотентности (idempotency keys), машины состояний статусов, интеграции с платёжным провайдером и вебхуков. Чаты требуют WebSocket/SSE. Ничего из этого не заложено.
4. **Нет пагинации и контракта ошибок.** Каталог туров и админ-списки без пагинации не переживут реальных данных. Формат ошибок (`detail`) нигде не зафиксирован как контракт.
5. **Безопасность отложена «на потом»,** хотя в API уже есть админ-операции (см. §7).

### Вердикт

Фундамент (auth) — 7/10, добротно. План развития API — **отсутствует как артефакт**, и это главный риск проекта: UI на четырёх платформах готов, а сервер на 10 % от него. Рекомендую до написания следующего эндпоинта создать `API_PLAN.md` + OpenAPI-спеку.

## 7. Критика сделанного

### Архитектурное (главное)

1. **Четырёхкратная дублирование — стратегическая ошибка.** Expo уже собирается в iOS, Android и Web. Параллельные нативные iOS (SwiftUI), Android (Compose) и отдельный Web (Vite) означают **×4 стоимость каждой фичи**. Матрица §12 это уже доказывает: функции расползлись (геолокация только в Expo, бронирование отсутствует на Android, авторизация на iOS — мок, 20 туров в Expo против 12 на Web/Android). Ни одна платформа не имеет полного набора функций.
2. **Мок-данные скопированы в 4 местах и уже разошлись** (20 vs 12 туров, 12 vs 8 городов). Нет единого источника истины даже для демо-контента.
3. **iOS-клиент вообще не подключён к API** — весь авторизационный флоу там фикция.

### Безопасность

4. **Refresh-токен передаётся в query string** (`GET /auth/refresh?refresh_token=...`, `GET /auth/logout?...`) — токены оседают в логах серверов, прокси и истории. Должно быть `POST` с телом (это проблема и клиента, и бэкенда).
5. **Захардкоженные учётные данные админа** (`admin` / `Lotofond`) прямо в клиентском коде и в документации. Клиентская «авторизация» админ-панели — декорация: весь админ-UI доступен любому, кто прочитал бандл.
6. **Токены в localStorage на Web** — уязвимы к XSS. Для Web правильнее httpOnly-cookie для refresh-токена.
7. **«Верификация ФНС» — мок,** при этом флоу выглядит для пользователя как настоящий. До продакшена нужна реальная интеграция (DaData / API ФНС).

### Дизайн API

8. Глаголы в URL и неконсистентные методы: `PATCH .../update-role`, `POST .../activate`, но `DELETE .../deactivate` (DELETE семантически означает удаление ресурса, а не смену флага). Чище: `PATCH /users/{id}` с полями `role`, `is_active`.
9. `GET /auth/logout` — мутация через GET (кэшируемый, prefetch-уязвимый метод).
10. Рассинхрон enum ролей (`moderator` vs `manager`) между API-типами и доменными типами.

### Качество

11. **Тестов почти нет:** 2 файла на Web, ноль на Expo/iOS/Android — при четырёх кодовых базах регрессии неизбежны.
12. В `authFetch` при провале refresh токены очищаются молча, вызывающий код получает исходный 401 без сигнала «сессия умерла» — нет единого механизма разлогина по всему приложению.
13. `rork.json` содержит дубль записи `expo`.
14. `Tour` — монолит из 26+ полей без разделения на карточку списка и детальную модель; при переводе на API это заставит листинг тащить полный объект (или ломать типы).

## 8. Предлагаемые оптимизации

### Стратегические (наибольший эффект)

1. **Сократить число платформ.** Рекомендация: оставить **Expo как основную** (она покрывает iOS + Android + Web через expo-router и уже самая полная — см. §12) и заморозить нативные iOS/Android до появления бизнес-причины (виджеты, особая производительность). Если Web-версия нужна как отдельный SEO-сайт — оставить `web/`, но выпилить из неё дублирующий мобильный функционал. Это в разы снижает стоимость каждой следующей фичи.
2. **Contract-first API.** Завести OpenAPI-спеку в репозитории, генерировать из неё типы: `openapi-typescript` для Expo/Web (общий пакет), Swift OpenAPI Generator для iOS, `openapi-generator` (kotlin) для Android. Расхождения типов исчезают по построению.
3. **Roadmap API по доменам** (порядок по ценности/стоимости):
   1. `GET /tours`, `GET /tours/{id}`, `GET /cities` — read-only каталог с пагинацией и фильтрами (заменяет 90 % моков);
   2. бронирования + платёжный провайдер (ЮKassa/CloudPayments) с идемпотентностью и вебхуками;
   3. избранное/отзывы/Reels (синхронизация UGC);
   4. партнёрский кабинет + реальная верификация ФНС (DaData);
   5. модерация и админ-инструменты;
   6. чаты (WebSocket/SSE) и push-уведомления.

### Тактические

4. Перевести refresh/logout на `POST` с токеном в теле; на Web — refresh в httpOnly-cookie.
5. Убрать хардкод админ-доступа; доступ к админ-панели — только по роли из `whoami`.
6. Выровнять enum ролей (`manager` vs `moderator`) на всех платформах — сейчас это готовый продакшн-баг.
7. Вынести мок-данные в один JSON-пакет (или сразу отдать бэкенду как seed) вместо четырёх копий.
8. В `authFetch` добавить событие «сессия истекла» (callback/EventEmitter), чтобы приложение централизованно разлогинивало пользователя.
9. Разделить `Tour` на `TourCard` (листинг) и `TourDetail` (полная модель) до перевода каталога на API.
10. Добавить пагинацию (`limit/offset` или cursor) во все списочные эндпоинты с первого дня.
11. Минимальный контур тестов: unit на фильтры/сортировку каталога (чистая логика, легко тестируется) и на token-refresh-флоу — две самые рискованные зоны.
12. Починить дубль в `rork.json`.

## Итог (TL;DR)

Проект — впечатляюще полная **витрина** агрегатора экскурсий на 4 платформах, но продукт держится на мок-данных: реальный API покрывает только авторизацию и пользователей (~10 % функциональности). Два главных решения, которые стоит принять сейчас: **(1)** сократить дублирование платформ (Expo уже покрывает все три таргета), **(2)** перейти к contract-first разработке API с явным roadmap: каталог → бронирования/платежи → UGC → партнёрка → модерация → чаты. Из срочного по безопасности: refresh-токен в query string, захардкоженный пароль админа в клиенте и токены в localStorage.
