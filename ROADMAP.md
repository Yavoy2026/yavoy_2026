# Roadmap бэкенда YaVoy

**Дата:** 13 июля 2026
**Принцип:** сначала минимальная цепочка, приносящая деньги (каталог → auth → бронь → оплата), всё остальное — в backlog с явными триггерами «когда делать». Никакой функционал не строится «на будущее».

Спека (модель данных, эндпоинты, соглашения) — в `BACKEND_SPEC.md`; roadmap ссылается на её разделы.

---

## Сделано вне карты

- **Панель управления отделена от витрины (сен 2026).** Бэкофис жил внутри витринного
  `Layout` и делил с ней контексты: под таблицей модерации висел футер с марками
  платёжных систем, снизу лезла навигация покупателя, вкладки хранились в `useState` —
  ссылку на раздел было не отправить, «назад» не работал. Теперь `/admin` со своим
  `AdminLayout`, разделы — отдельные адреса, переходы перезагрузкой документа (решение
  владельца: лишние полсекунды дешевле, чем протечки стейта между разделами).
  `/backoffice` редиректит, API и мобильная админка не тронуты.

  Следом панель получила собственный стиль: свои примитивы `components/admin/ui.tsx`
  (плотные таблицы вместо витринных карточек, мелкий радиус, нейтральная палитра,
  фирменный акцент только на статусах и опасных действиях). Из профиля витрины убраны
  вход в панель и переключатель языка — он переехал в шапку и в настройках дублировался.

  Счётчики на разделах (сколько заявок, сколько отзывов) сняты: они брались из запросов
  соседних вкладок, а при разделении это означало бы тянуть их на каждой странице.
  Вернуть — отдельным эндпоинтом `/admin/counts`, если понадобится.

- **YAV-21 — эквайринг узбекской инсталляции (сен 2026).** Провайдер за интерфейсом
  `PaymentProvider`, реализация для OCTO (`secure.octo.uz`, одностадийная оплата):
  таблица `payments`, статус брони `pending_payment`, коллбэк `/v1/webhooks/octo`
  с проверкой подписи, сборщик неоплаченных броней, возвраты. Валюта и провайдер —
  параметры инсталляции (`CURRENCY`, `PAYMENT_PROVIDER`), мультивалютности в коде нет.
  Плюс требования банка к сайту: оферта, политика конфиденциальности, акцепт перед
  оплатой, марки платёжных систем.

  Осталось: реквизиты магазина из кабинета merchant.octo.uz, ключ подписи коллбэков
  от техподдержки, тестовая транзакция в песочнице, фискализация чеков (basket/ИКПУ),
  заполнить реквизиты в оферте, узбекский каталог (сейчас на стенде демо-туры по РФ).

- **Валюта инсталляции доведена до конца (сен 2026).** `CURRENCY` до этого нигде не
  читалась: сид и все клиенты были жёстко прибиты к рублю, и узбекская витрина ушла бы
  в OCTO с `currency: "RUB"`. Теперь код валюты уезжает клиентам в `GET /v1/config`,
  проставляется новым турам и броням на сервере, а символ подставляет UI
  (`CURRENCY_SYMBOL` в `@yavoy/i18n`) — 45 захардкоженных `₽` вычищены на обеих
  платформах вместе с полем `currency` в легаси-типах витрины. Денежные колонки
  переведены на `bigint` (миграция `0007`): в int4 помещается 21,5 млн сум, что
  пробивается групповой бронью. Заодно починены прод-Dockerfile'ы обоих клиентов —
  они не копировали `packages/i18n`/`packages/legal` и не собирались с самого YAV-25.

- **Мелочи витрины, вскрытые на узбекском стенде (сен 2026).** Переключатель языка
  стоял только в профиле — гостю недоступен, хотя инсталляция может стартовать на
  незнакомом ему языке; перенесён в шапку. `NO_DATE_FALLBACK` (`2099-12-31`) —
  служебная заглушка сортировки для туров без дат — печаталась в карточке как
  настоящая ближайшая дата и в Expo пропускала такие туры под любой фильтр по дате.
  У `<main>` не было `padding-bottom`: контент упирался в футер на всех страницах.

- **YAV-25 — мультиязычность (сен 2026).** Интерфейс обоих клиентов на ru/en/uz
  (узбекский — латиница, черновой перевод, нужна вычитка носителем). Каталог переводов —
  `packages/i18n` (собственное ядро вместо i18next: плюрализация по правилам CLDR,
  без зависимости от Intl в Hermes). Язык по умолчанию отдаёт бэкенд через
  `GET /v1/config`, письма — на `MAIL_LOCALE`. Ошибки переводятся по стабильному коду.
  Контент каталога сознательно не переводится. `tours.languages` переведён на коды
  (миграция `0005_tour_languages_codes`). Страж от регрессий — `pnpm i18n:check`.

  Осталось по теме: вычитка узбекского носителем; юридические тексты (условия
  использования, оферта, согласие на ПДн) остаются русскими — их перевод требует юриста.

## Карта пути

```
M0 Каркас → M1 Каталог → M2 Auth → M3 Брони-заявки → M4 Оплата   = MVP (деньги)
                                                        ↓
                                        M5 Избранное + отзывы     = retention-минимум
                                                        ↓
                                        Backlog по триггерам (партнёрка, админка, Reels, ...)
```

Оценки — для соло-разработки с AI-ассистентом, чистыми днями.

---

## M0 — Каркас и деплой (~2–3 дня)

**Цель:** пустой API живёт в проде, деплой — одна команда.

Задачи:
- [ ] pnpm-workspace: `apps/backend`, `packages/contracts`; `expo/` пока **не трогаем** (переезд в `apps/` — отдельным шагом позже, чтобы не смешивать риски)
- [ ] Скелет Fastify 5 + `fastify-type-provider-zod` + `@fastify/swagger` (OpenAPI на `/docs`)
- [ ] Drizzle + drizzle-kit, пустая миграция, подключение к Postgres
- [ ] `docker-compose.yml`: postgres + backend + caddy (**Redis не добавляем** — понадобится только в M4)
- [ ] Единый error-handler (конверт ошибок из спеки §2), pino-логи, Sentry
- [ ] CI: lint → typecheck → vitest → build; деплой на VPS (git pull + compose up)
- [ ] `GET /v1/health`

**DoD:** `curl https://<домен>/v1/health` → 200 из прода; CI зелёный.
**Осознанно не делаем:** staging-окружение, k8s, мониторинг сложнее Sentry.
**Решить до старта:** домен API (вопрос №1 из спеки §8), выбор VPS.

## M1 — Каталог read-only (~3–5 дней)

**Цель:** приложение показывает туры из БД; главный экран перестаёт быть витриной на моках. Auth не нужен — каталог публичный.

Задачи:
- [ ] Миграции: `cities`, `tours`, `tour_media`, `tour_dates` (таблица дат создаётся сейчас, заполняется в M3)
- [ ] Seed-скрипт: конвертация `expo/mocks/tours.ts` + `cities.ts` (20 туров, 8 городов) в БД — единственное место, где моки ещё пригодятся
- [ ] zod-контракты в `packages/contracts`: `TourCard` (усечённая — для списка), `TourDetail`, `City`, параметры фильтров
- [ ] `GET /cities`, `GET /tours` (фильтры: city, duration, transport, interest[], category[], season, price, `q`, sort, cursor), `GET /tours/{id}`
- [ ] Поиск `q` — пока `ILIKE` по title/description/city (FTS с русской морфологией — в backlog)
- [ ] Expo: экраны «Экскурсии», «Направления», «Детали тура» → React Query на API; **удалить `mocks/tours.ts`, `mocks/cities.ts`, `mocks/categoryTours.ts`** (~2800 строк)

**DoD:** приложение из TestFlight/Expo Go показывает каталог из прода; фильтры и сортировка работают; моки каталога удалены из репо.
**Осознанно не делаем:** отзывы (в деталях тура — пустая секция), фильтр по дате (нет данных в `tour_dates`), кэширование (20 туров), FTS.

---

## M2 — Auth + профиль (~4–6 дней)

**Цель:** свой auth вместо чужого `yavay.ru`; фундамент для броней.

Задачи:
- [x] Миграции: `users`, `refresh_sessions`
- [x] JWT RS256 (ключи в env), пара access/refresh, **ротация refresh** с детекцией повторного использования (спека §4)
- [x] ~~signup/signin с паролем~~ → **авг 2026: passwordless OTP** (`POST /auth/otp/request|verify`, `is_new_user`; пароли и argon2 удалены), `POST /auth/refresh|logout`, `GET /auth/whoami`
- [x] `PATCH /users/me` (~~/me/password~~ — не нужен без паролей)
- [ ] Rate-limit: 5/мин/IP на auth-эндпоинты
- [ ] Auth-плагин Fastify (guard по JWT + роль) — переиспользуется всеми следующими фазами
- [ ] Expo: `AuthProvider` и `services/api.ts` → новый API (контракт близок к старому — миграция дешёвая); **удалить хардкод `admin`/`Lotofond`** и скрыть кнопку админ-панели (админки пока нет)
- [ ] Тесты: полный auth-флоу, ротация, повторное использование refresh

**DoD:** регистрация/вход/автопродление сессии работают из приложения на проде.
**Осознанно не делаем:** фото профиля (нужен S3 — тянем в M5+/backlog), OAuth/соцсети.
**Авг 2026:** восстановление пароля стало не нужно — вход по OTP (вход = восстановление). Открытый вопрос: SMTP-провайдер (без него коды видны только в логах сервера).

## M3 — Бронирования-заявки, без онлайн-оплаты (~4–5 дней)

**Цель:** пользователь может забронировать; бизнес получает лиды и подтверждает вручную. Деньги — пока офлайн (перевод/на месте). Это самый ранний момент, когда продукт начинает работать по-настоящему.

Задачи:
- [ ] Заполнить `tour_dates` (ручной seed по реальным датам), включить фильтр по дате в каталоге
- [ ] Миграция `bookings` (спека §3.2, но статусы упрощены: `requested | confirmed | completed | cancelled` — `pending_payment` появится в M4)
- [ ] `POST /bookings` (auth, транзакция с `SELECT FOR UPDATE` на `seats_left`, `CHECK (seats_left >= 0)`), `GET /me/bookings`, `POST /bookings/{id}/cancel`
- [ ] Подтверждение брони: пока **вручную** — эндпоинт `POST /bookings/{id}/confirm` под ролью `admin` (вызов через curl/Swagger UI, без админ-UI)
- [ ] Email через SMTP (Unisender/Mailopost): письмо админу о новой заявке, письмо клиенту о подтверждении с кодом
- [ ] Expo: модальное окно бронирования → API; секция «Мои бронирования» в профиле → API

**DoD:** заявка из приложения → письмо админу → confirm → клиент видит подтверждённую бронь с кодом.
**Осознанно не делаем:** онлайн-оплату, автоотмену по TTL (без денег заявка не «протухает» критично), ваучеры-PDF.

---

## M4 — Онлайн-оплата ЮKassa (~5–8 дней) → **конец MVP**

**Цель:** деньги проходят без участия человека.

Задачи:
- [ ] Добавить Redis + BullMQ в compose (первая реальная необходимость)
- [ ] Миграция `payments`; статус брони `pending_payment`, полная машина состояний через таблицу переходов (спека §1.3, правило 1)
- [ ] `POST /bookings` → создание платежа ЮKassa → `payment_url` клиенту; `Idempotency-Key`
- [ ] `POST /webhooks/yookassa`: верификация источника, идемпотентная обработка, `pending_payment → confirmed`
- [ ] Джоба `booking-ttl`: 30 мин без оплаты → отмена + возврат мест
- [ ] Джоба `booking-complete` (cron): прошедшая дата → `completed`
- [ ] Расчёт возврата при отмене — чистая функция по `cancellation_policy`; сам возврат денег — пока вручную из кабинета ЮKassa
- [ ] `GET /me/transactions`
- [ ] Expo: оплата через WebBrowser (redirect на ЮKassa), экран статуса оплаты, транзакции в профиле

**DoD:** тестовый платёж в песочнице ЮKassa проходит цепочку заявка→оплата→confirmed→email автоматически; неоплаченная бронь отменяется через 30 мин.
**Блокер, решить заранее (в M2–M3):** юрлицо + договор с ЮKassa + комиссионная модель (вопросы №2–3 спеки §8) — оформление занимает недели, запускать параллельно с разработкой.

---

## M5 — Избранное + отзывы (~3–4 дня) — retention-минимум

- [ ] `favorites`: `GET /me/favorites`, `PUT|DELETE /me/favorites/{tour|city}/{id}`; Expo: миграция локального избранного на сервер при входе
- [ ] `reviews`: `POST /bookings/{id}/review` (только `completed`, UNIQUE на бронь), `GET /tours/{id}/reviews`, `GET /me/reviews`
- [ ] Модерация отзывов: `status=pending` по умолчанию, approve — через admin-эндпоинт (curl/Swagger, UI не строим)
- [ ] Пересчёт рейтинга тура при публикации отзыва

**DoD:** избранное синхронизировано между устройствами; отзыв после завершённой поездки виден в каталоге.

## Сводка

- **MVP = M0–M4 ≈ 18–27 рабочих дней** (реалистично 4–6 недель календарно). После M4 продукт продаёт.
- После каждого майлстоуна — рабочий прод и удалённый кусок моков; ни один майлстоун не зависит от backlog-блоков.
- Самый длинный внешний lead time — договор с ЮKassa: **запустить оформление во время M2**, не позже.
- ~~Партнёрка и админ-панель откладываются~~ → авг 2026: заказчику понадобились раньше триггеров — сделаны базовые версии (веб-бэкофис `/backoffice`, ныне `/admin`; роль partner, CRUD туров).
